Architecture guide

Microservice control plane

Use Flaxon Admin as one operational control plane while each microservice owns its database, business rules, and migrations. The Admin communicates through authenticated service APIs; it never reaches into another service's database.

Register services

The control plane is mounted by default with AdminDashboard. Use a persistent Admin store in every worker and configure Redis for sessions, locks, rate limits, and cross-worker events.

from flaxon import Flaxon
from flaxon.admin import AdminDashboard, AdminStore

app = Flaxon("operations")
admin = AdminDashboard(
    app,
    store=AdminStore("admin.sqlite3"),
    redis_url="redis://127.0.0.1:6379/0",
    users=[{
        "username": "admin",
        "password": "load-this-from-a-secret-manager",
        "roles": ["administrator"],
    }],
)

# The service remains the authority for its records.
# Register connection and ownership metadata through the control-plane API.

Service-owned Admin models

Expose a stable JSON contract from the service and connect it to Admin with RemoteServiceClient and RemoteModelAdapter. List responses may be a JSON array or {"items": [...]}; detail, create, update, and delete use the corresponding resource endpoints.

from flaxon.admin import RemoteModelAdapter, RemoteServiceClient

catalog = RemoteServiceClient(
    "https://catalog.internal",
    token=service_token,
    timeout=3,
    retries=2,
)
products = RemoteModelAdapter(catalog, "products")
admin.register(
    products,
    name="product",
    fields=["id", "name", "price", "status"],
    list_display=["id", "name", "price", "status"],
)

Custom Admin modules

Use FlaxonModule for reports, support tooling, billing pages, or service-specific workflows. A module can own routes, Jinax templates, static assets, hooks, dependencies, and CLI commands.

from flaxon.modules import FlaxonModule

reports = FlaxonModule("reports", template_dir="reports/templates")

@reports.get("/summary")
async def summary():
    return {"service": "reports", "status": "ready"}

admin.mount_module(
    reports,
    prefix="/admin/extensions/reports",
    navigation=[{"name": "Reports", "path": "summary"}],
)

# URL: /admin/extensions/reports/summary

Events and reliable commands

Publish an event after the service transaction commits. Use an outbox and a broker such as Redis Streams, RabbitMQ, or Kafka for production delivery. Consumers must be idempotent because retries can deliver an event more than once.

event = admin.control_plane.events.publish(
    "OrderCreated",
    {"order_id": "ord_123", "tenant_id": "tenant_42"},
)

# Typical events: ProductStockReserved, UserDeactivated,
# PostPublished, and MediaUploaded.

Gateway and security responsibilities

  • Terminate TLS and route /admin, /cms, and versioned service APIs.
  • Validate identity, tenant, and scopes before forwarding requests.
  • Propagate request IDs and trace IDs through every service.
  • Use idempotency keys, timeouts, retries, circuit breakers, and dead-letter queues for cross-service commands.
  • Keep service tokens scoped, rotated, and stored in a secret manager.

Production checklist

  • Give every service its own database and migration history.
  • Use Redis-backed sessions, rate limits, locks, and WebSocket fan-out when running multiple workers.
  • Run durable task workers separately from web processes.
  • Store media in S3-compatible object storage with signed URLs and background scanning.
  • Keep audit records append-only and apply a documented retention policy.
  • Treat the built-in registry as an operational catalog, not a replacement for service discovery.
